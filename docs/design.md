# Sign-out App — Design Suggestions

Starting points: your gastric biopsy (v8) and colonic polyp single-file HTML apps, and the QMH [Cancer Reporting Templates](https://awiloqmh.github.io/CancerReportingTemplate/) (CAP-based, Jun-2026 version) for resections.

## 1. What the two starting points already give you

| | Your biopsy apps | QMH templates |
|---|---|---|
| Structure | Per-part tabs (A–J), `parts[]` array of field values, `buildMicroscopy()` + `buildDiagnosis()` | One static HTML page per organ; `<select>`/`<input type=checkbox>` with IDs `A01…A68`; option `value` already holds the output text (`"  - Cecum"`) |
| Output | Narrative microscopy paragraph + `(A) STOMACH, antrum, biopsy -` diagnosis lines | `updateDescription()` concatenates `- Element: value` lines into a textarea; `CopyToClipboard()` |
| Staging | n/a | pT/pN/pM chosen manually from dropdowns; no auto-derivation, no stage group |
| Persistence | None (reload = lost) | None |
| Multi-part cases | Yes | No (one specimen per page) |

The gap to close: one case-level app where each part picks a template, with narrative, synoptic and hybrid generators sharing a single engine, and output written to Drive in the same shape as your existing draft Docs.

## 2. Core architecture: templates as data, not code

Each organ/specimen type becomes a JSON schema, rendered and generated by one engine, instead of a new hand-coded HTML file per specimen.

```json
{
  "id": "gastric_biopsy",
  "version": "2026.09",
  "specimenNoun": "biopsy",
  "organ": "STOMACH",
  "fields": [
    {"id": "site", "label": "Site", "type": "select", "options": ["Antrum","Body","Incisura","Cardia","Superficial gastric mucosa"]},
    {"id": "activity", "label": "Activity", "type": "grade", "options": ["Absent","Mild","Moderate","Marked"], "default": "Absent"},
    {"id": "imType", "label": "IM type", "type": "select", "options": ["Complete","Incomplete","Mixed"], "showIf": {"imDegree": "!=Absent"}},
    {"id": "hp", "label": "H. pylori", "type": "select", "options": ["Absent","Rare","Moderate density","Numerous"]}
  ],
  "generators": {
    "microscopy": "gastric_micro.js",
    "diagnosis": "gastric_dx.js",
    "synoptic": null
  },
  "snippets": ["hp_comment", "im_surveillance_comment"]
}
```

Why: adding prostate or IBD becomes writing a schema plus two small generator functions; the UI, part tabs, Drive export, validation and tests are shared. Your v8 `parts[]` object is already 90% of this schema — start by extracting it.

### Case model

```
Case
  accession        "26S-012345" (normalised zero-padding — your Drive names are inconsistent)
  clinicalHistory  free text
  parts[]          { label: "A", templateId: "gastric_biopsy", specimenName: "Antrum", values: {...}, blocks: "A1" }
  reportMode       "narrative" | "synoptic" | "hybrid"
  status           "draft" | "ready" | "signed"
  outputs          { macro, blockKey, micro, diagnosis, synoptic }
```

Key point: one case can mix templates (A gastric antrum, B duodenal biopsy, C colonic polyp) — this is the main thing the per-app approach cannot do and reflects real OGD/colonoscopy requests.

## 3. Output engine: three generators, one style layer

1. **Narrative microscopy** — sentence builder with grammar rules (list joining, plural handling, "with/and" merging) so combined micro + IHC read as one paragraph, per your preference.
2. **Diagnosis lines** — the `(A) ORGAN, site, procedure -` convention you already use, with capitalisation rules from the colonic polyp app (only organ/site and diagnosis capitalised).
3. **Synoptic block** — CAP-style `- Element: value` lines, produced from the same `values`, with required-element checking.

**Hybrid** = narrative microscopy paragraph + synoptic block for the core data elements (type, grade, extent, margins, nodes, pTNM) + diagnosis line. Make the mode a per-case toggle so the same input yields any of the three.

A shared **style layer** enforces British spelling, plain ASCII (LIS-safe: no smart quotes, µ→"micro", ≥→">="), line width, and blank-line conventions, so no generator has to think about it.

**Golden-output tests**: keep fixture inputs → expected report text for each template (e.g. your "Load example" cases). Any wording refactor that changes output fails a test — this protects the phrasing you have tuned over eight versions.

## 4. Synoptic and AJCC layer (building on QMH)

- **Import rather than retype.** The QMH pages are regular enough to parse: each `<select>`/checkbox has an ID and its `value` is the output text; the `updateDescription()` function encodes element labels and order. A one-off converter script can turn each page (colon, stomach, prostate, breast, etc.) into a JSON schema, then you curate. Keep a `source` field pointing at the CAP protocol PDF/page so each element links to its reference, as QMH does.
- **Add what QMH lacks:**
  - Auto-derive pT/pN/pM from extent, node counts and metastasis fields, with a visible "override" toggle and reason.
  - Stage-group lookup tables per protocol version (AJCC 8th; 9th where adopted), stamped into the output (`AJCC 8th ed.`).
  - Validation before export: required CAP elements, node count present if pN given, margin status for every listed margin, Gleason pattern sum = score.
  - Derived values: node ratio, largest deposit, % involvement, tumour budding category from count, Ryan score from description.
- **Version pinning**: store `templateVersion` in each saved case so re-opening an old case renders with the schema it was signed under.

## 5. Google Drive as the single source of truth

Requirement: every case must be readable from Perplexity in a browser, so Drive is the primary store, not a sync target. No local-first storage; the browser holds only a transient cache.

Match the shape your TAT/completeness workflow already parses: a Google Doc named by normalised accession number in the "Pathology reports" folder, with sections **Clinical history/specimen title → Macroscopic description → Block key → Microscopic description → Diagnosis / Synoptic report**.

- **Two Drive artefacts per case, both visible to Perplexity's Drive connector:**
  1. The Google Doc (human-readable report, what the TAT job and Perplexity read and edit).
  2. A row in a `Sign-out cases` Google Sheet: accession, date, status, templates, mode, Doc link, and a `case_json` column holding the full structured state. Sheets are searchable and readable through Perplexity, unlike Drive `appProperties` or hidden metadata, so avoid those.
- **Reopen from Drive**: the app's case list is the Sheet; opening a case loads `case_json`, re-renders the form, and regenerates output. Editing is always against Drive state.
- **Idempotent save**: search the folder by normalised accession → update Doc if present, else create; upsert the Sheet row by accession. Never duplicate.
- **Auth**: Drive REST API + Google Identity Services in the browser with `drive.file` scope (only files the app created) plus `spreadsheets` for the case Sheet — no server. Fallback: a Google Apps Script web app bound to the Sheet, if OAuth setup stalls.
- **Transient cache only**: keep the in-progress case in `sessionStorage` so a refresh does not lose work; clear it on successful save. Any "pending save" indicator is a bug to fix, not a feature.
- Keep "Copy diagnosis" and "Copy full report" for pasting into the LIS.

**Perplexity round-trip**: because reports and structured data both live in Drive, you can ask Perplexity to review a draft Doc, rewrite microscopy in your style, check a synoptic against the CAP protocol, or run analytics across the Sheet (H. pylori rate, adenoma detection, Grade Group distribution) without exporting anything.

Data-governance note: only accession numbers and report text should reach a personal Drive, never names/HKIDs. Enforce with a regex guard on free-text fields before save.

## 6. UX suggestions

- **Keyboard-first**: number keys select options within a focused field; Tab/Shift-Tab moves between fields; `Cmd+Enter` = generate; `Cmd+Shift+C` = copy diagnosis. Fast sign-out of a 10-polyp case should need no mouse.
- **"Normal" defaults per template** and a one-key "all normal" per part, then edit exceptions.
- **Live preview pane** (as in v8) with diff-highlighting of the lines changed since last generate.
- **Snippet library**: reusable comments (H. pylori eradication advice, SSL/IM surveillance, IBD dysplasia caveat) inserted by template or by hand, stored as Markdown you can edit outside the app.
- **Part duplication**: "same as A" copies values to B–J, then adjust site.
- **Case queue**: list of unsent/draft cases with accession, template, age — pairs naturally with the TAT list.
- **Dark mode, iPad-width layout**, consistent with PathExam's look so switching between them is frictionless.

## 7. Template roadmap (small biopsies first)

| Template | Notable logic |
|---|---|
| Gastric biopsy (existing) | Sydney elements; site-aware "superficial mucosa" handling |
| Colonic polyp (existing) | Up to 10 parts; HGD option; SSL/TSA; site capitalisation rules |
| Prostate biopsy | Cores A–L; per-core Gleason, length/%, number of cores positive; auto Grade Group, aggregate and worst-core summary; PNI, EPE, IDC-P, HGPIN/ASAP; summary table line for the report |
| IBD biopsy | Multi-site mapping (terminal ileum → rectum); chronicity, activity grade, basal plasmacytosis, granulomas, crypt architecture; dysplasia; optional Nancy index; derived summary ("chronic active colitis, distribution consistent with …") |
| Duodenal biopsy | Marsh–Oberhuber, IEL count, villous architecture, H. pylori, giardia |
| Oesophageal biopsy | Barrett's with dysplasia grading, eosinophil count/hpf, reflux changes |
| Endometrial / LEEP | Port from your earlier apps into schemas |
| Resections (synoptic/hybrid) | Imported from QMH schemas + staging layer, starting with colon, stomach, prostate, breast |

## 8. Suggested build order

1. Extract the v8 `parts[]` fields into a JSON schema; write the generic renderer; confirm golden outputs match v8 and the colonic polyp app exactly.
2. Add the case model, mixed-template parts, autosave, copy buttons.
3. Drive export (Doc + appProperties + Sheet row), idempotent save, accession normalisation.
4. Prostate and IBD schemas.
5. QMH → JSON converter; colon resection as the first synoptic/hybrid template with auto pTNM and validation.
6. Snippet library, case queue, keyboard polish.

## 9. Stack

Single-page app, vanilla JS or Preact/Svelte, no build step required (keeps the single-file-HTML feel you already have). Host on GitHub Pages (like QMH) so it is reachable from any browser, including alongside Perplexity, with no Mac mini or Tailscale dependency. Schemas and snippets as plain JSON/Markdown files under version control; store a copy of the schema set in Drive too if you want Perplexity to reference field definitions. Node-based test runner for golden outputs.
