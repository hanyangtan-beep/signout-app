# Sign-out App — Roadmap

Companion to "Sign-out App — Design Suggestions". Phases are sequential; each ends with a usable app so you can sign out real cases from Phase 1 onward. Effort estimates assume evening/weekend work with AI-assisted coding.

---

## Phase 0 — Foundations (1 weekend)

**Goal:** a repo, a test harness, and a frozen record of current behaviour before anything is refactored.

- Create repo `signout-app/` with `schemas/`, `generators/`, `snippets/`, `tests/fixtures/`, `src/`.
- Copy gastric-biopsy-signout-v8.html and colonic-polyp-signout.html into `legacy/`.
- Capture golden fixtures: for each app, 5–8 input states (normal, H. pylori gastritis with IM, HGD adenoma, 10-part polyp case, etc.) → exact microscopy and diagnosis text output.
- Node test runner (`node --test`) that will later assert the new engine reproduces these byte-for-byte.
- Hosting: built and published inside Perplexity to a private `pplx.app` URL (static app, no PHI in the code; all case data lives in Drive). No GitHub, no Mac mini.
- The Google Cloud OAuth client needs the final pplx.app origin, so it is created at the start of Phase 2, right after the first publish fixes the subdomain.

**Done when:** `npm test` runs the fixtures against the legacy generator functions and passes. ✅ Completed 2026-09-09 (16 fixtures, 18 tests, DOM cross-check).

## Phase 1 — Schema engine and parity (2–3 weeks)

**Goal:** one generic app that renders any schema and reproduces both legacy apps exactly.

- Define the schema format: `fields[]` (select / grade / checkbox / number / text), `default`, `showIf`, `group`; `generators` (microscopy, diagnosis, synoptic); `organ`, `specimenNoun`, `maxParts`.
- Write `schemas/gastric_biopsy.json` and `schemas/colonic_polyp.json` by extracting the v8 `parts[]` fields and the polyp app options.
- Port `buildMicroscopy()` / `buildDiagnosis()` into `generators/gastric.js` and `generators/colonic.js` as pure functions `(partValues, ctx) → string`.
- Generic renderer: part tabs A–J, field groups, live preview, Generate / Copy diagnosis / Copy report / Clear / Load example.
- Style layer: British spelling table, ASCII normalisation, capitalisation rules for diagnosis lines, paragraph joining.
- In-memory case state with `sessionStorage` cache when available (the in-thread preview blocks storage; the published site allows it).
- Deploy the in-thread preview for visual QA, then publish to `https://<subdomain>.pplx.app` (you pick the subdomain, e.g. `signout`). This fixes the origin needed for the OAuth client.

**Done when:** all Phase 0 fixtures pass through the new engine unchanged, and you sign out a week of gastric/polyp cases in it without falling back to the old apps. ✅ Engine, schemas, generic UI and in-thread preview completed 2026-09-09 (27 tests: 16 golden fixtures + 11 engine tests). Publishing to pplx.app happens when you choose the subdomain; the week of live use is yours to run.

## Phase 3 — Case model and mixed parts (1–2 weeks)

**Goal:** a case is the unit of work, not a template.

- [x] Case object (2026-09-10): accession, clinical history, macro, block key, status, options and parts with per-part `templateId` — serialised as the `case_json` saved in Phase 2. Older rows without `templateId` fall back to the case `schemaId`. The Sheet's `template` column and the Doc footer record every template used (`gastric_biopsy+colonic_polyp`).
- [x] Per-part template picker (2026-09-10): each part panel has a template drop-down; the header template buttons start a new case while the case is untouched and switch the *active part* once it has been edited. `+ Part` inherits the active part's template; "Same as previous" copies the template too. Part tabs show the template on hover; the status line reads `Mixed: Gastric + Polyp · 3 parts`.
- [x] Case-level output assembly (2026-09-10): `engine.generateCase(registry, caseState)` runs each part through its own generator and style, keeps case order in every block, merges template options, and runs per-template hooks (`prepare`, `summary`) over that template's parts only — so a prostate SUMMARY counts prostate cores, not gastric parts. A generator's case-level `specimens` rewrite (gastric title parsing) is used only when the whole case is one template. Doc layout: accession → clinical → macro → block key → microscopy → diagnosis.
- [x] Single-part cases drop the part letters (2026-09-09): when a biopsy case has only one part, the specimen, microscopy and diagnosis lines are emitted without "(A)" (`STOMACH, antrum, biopsy - CHRONIC GASTRITIS…`). Letters appear automatically once a second part is added. Implemented in `engine.generate` (`dropPartLetters`) so every template inherits it, including gastric and polyp; the legacy golden fixtures pass `options.alwaysLetter` to keep their lettered form.
- [x] Engine extensions (2026-09-09): parts A–Z (`maxParts` per schema), `partDefaults` (per-position defaults, e.g. a 12-core prostate map or the TI → rectum series), `defaultParts`, a `number` field type, and a `generator.summary(parts, ctx)` hook appended after the diagnosis lines.
- [x] Prostate and IBD templates pulled forward from Phase 4 (see below).
- [x] "Same as previous part" copy; "Reset" returns a part to its template's normal/absent defaults, which serves as "all normal".
- [x] Case list view over the Sheet (Open dialog): status badge, template(s), part count, last update; search by accession. Filtering by status is still a wish-list item.
- [x] Keyboard model: number keys for options, Tab between fields, `Cmd+Enter` copies the full report (generation is live), `Cmd+Shift+C` copy diagnosis, `Cmd+S` save to Drive, `Alt+←/→` between parts.

**Done when:** a 3-part mixed OGD + colonoscopy case produces a single coherent report, saves to Drive, and reopens from another browser. Report assembly and round-trip through the Sheet row are covered by `tests/mixed.test.js`; a real Drive save of a mixed case is the remaining acceptance check.

## Phase 4c — Frozen section sign-out templates (1–2 weeks)

**Goal:** report intraoperative consultations in the same app and carry the result into the final report automatically. 28 of the 600 Docs mention frozen sections; the recurring paraffin sentence is "The paraffin sections confirm the frozen section diagnosis."

- [x] **Frozen section template** (`schemas/frozen_section.json`, `generators/frozen.js`, 2026-09-10): each frozen specimen is a normal lettered part (the department letters frozen specimens A, B, C … and converts every frozen block to paraffin, so the same letters carry through to the final report — no separate FS1/FS2 lettering needed). Case fields: reported by (printed in brackets, e.g. "(Prof. A Cheung / Dr. HY Tan)"), phone-reported time and date, reported to (optional). Mixes with paraffin templates in one case; only frozen parts feed the intraoperative block.
- [x] **Frozen diagnosis pick-lists by scenario**, each generating a one-line intraoperative diagnosis; identical results are grouped "(A)-(D) No malignancy." as in the department's reports:
  - Margins: No malignancy / carcinoma present at margin (tumour type) / close (mm) / dysplasia only (grade) / atypical, deferred.
  - Lymph nodes: Negative for malignancy / macrometastasis / micrometastasis (size mm) / deferred.
  - Parathyroid identification: hypercellular / normocellular parathyroid / thyroid tissue / lymph node / adipose / thymic tissue.
  - Ovarian or adnexal mass: benign / borderline / malignant (favoured type) / deferred.
  - Nodule or mass (lung, thyroid, other): benign / malignant (type) / deferred.
  - Free text for anything else.
- [x] **Block handling**: per-part macroscopic description generated from pieces, tissue, measurement, handling and block count ("Received in a fresh state is a piece of tan coloured tissue measuring 1 x 0.4 x 0.2 cm. All embedded in 1 frozen block and subsequently converted to paraffin block."); toggle off if the macro is typed elsewhere. Engine gained optional `macro` and `intraop` blocks (order: SPECIMEN → MACROSCOPIC → INTRAOPERATIVE CONSULTATION → MICROSCOPIC → DIAGNOSIS); the Google Doc merges the generated macro with any typed macro.
- [x] **Frozen–paraffin correlation**: concordant → "(A) The paraffin section confirms the frozen section diagnosis. It shows … There is no evidence of dysplasia or malignancy."; discordant → reason (sampling / interpretation / technical) written into the microscopy and the paraffin diagnosis overrides the line; deferred → "The frozen section diagnosis was deferred. The paraffin section shows …".
- [x] **Output**: INTRAOPERATIVE CONSULTATION block before the microscopy ("(Prof. A Cheung / Dr. HY Tan)" / grouped results / "The frozen section diagnosis was phone reported at 1321 on 13/05/2026 to Dr Lee (OT 3)."), copy-ready from its own Copy button at the time of the call; diagnosis lines in house format "(A) TONGUE, medial margin, frozen section - NO EVIDENCE OF MALIGNANCY".
- [x] Save to Drive the moment the frozen result is called (existing Save; the Doc now carries the INTRAOPERATIVE CONSULTATION heading so the TAT job can see it).
- [ ] Time received and slides-dispatched times (department FS log) — add only if you want them in the report rather than the LIS log.
- [ ] Discordance summary for QA across cases (needs the Sheet query in Phase 5).

**Done when:** a margin-frozen SCC case and a parathyroid frozen are reported live from the app, the frozen line appears unchanged in the final Doc, and the correlation sentence is generated without typing. (Template built and tested 2026-09-10; live acceptance pending.)

## Phase 4d — Template organisation (1 week; build before Phase 4b fills the list)

**Why:** Phase 4 ends at about 12 small-biopsy templates, 4b adds ~20 benign resections and Phase 5 adds one synoptic template per cancer resection — 40–50 templates in total. The flat header row and the per-part `<select>` both stop working at about 10. Decided 2026-09-10.

**Organise by organ system, then by specimen size**

- Add `system` and `kind` metadata to every schema. `system` ∈ GI, Hepatobiliary, GU, Gynae, Breast, Thoracic, Head and neck, Skin, Cardiovascular, Lymphoid, Frozen. `kind` ∈ biopsy, benign resection, cancer resection (synoptic). The picker is a matrix: choose the system, templates appear in ascending specimen size (Colon: biopsy → polyp → IBD → resection). Phase 5 templates land in the third column of the same rows, not in a separate list.
- Rename `shortName` to "Organ · procedure" (Cervix · biopsy, Cervix · LEEP, Colon · resection) so ordering is self-evident. Header buttons keep the short organ label where unambiguous.
- [x] Rename the **Polyp** header button and `shortName` to **Colonic polyp** (added 2026-09-10; done 2026-09-10) — "Polyp" is ambiguous once endocervical, endometrial, nasal, gastric (fundic gland / hyperplastic) and skin polyps have their own templates or pick-lists; the same rule applies to any other bare procedure or lesion name (e.g. "Frozen" stays, but "Biopsy"-only labels are not allowed). Do this with the shortName change above and update the Small biopsy row layout (`Gastric  Colonic polyp  Duodenum …`).
- Per-schema `aliases` array for search ("TURBT", "chips", "Marsh", "coeliac", "LEEP", "Warthin", "pyogenic").

**Small biopsies get their own always-visible section** (added 2026-09-10)

Small biopsies are signed out daily, so they must never be more than one click away regardless of how many resection templates exist. The header carries a fixed **Small biopsy** section — every template with `kind: biopsy` (gastric, polyp, duodenum, oesophagus, IBD, prostate, breast core, cervix, endometrial, lung / bronchial, TURBT biopsy fragments, skin punch / shave) in one row, ordered by the daily TAT-list frequency, with the current template highlighted. This section is not subject to the pinned-strip cap and is shown by default even when the header is otherwise collapsed. Everything else (benign resections, synoptic cancer resections, frozen) sits behind a second **Resections** control that opens the grouped picker. Layout:

```
Small biopsy   Gastric  Colonic polyp  Duodenum  Oesophagus  IBD  Prostate  Breast  Cervix  Endometrium  Lung
Resections ▾   [pinned / recent ≤ 8]                                          ⌘K search
```

If the biopsy row itself outgrows one line (> ~12), it collapses to the top 8 by frequency plus a "more" overflow — still one click, never a search. The "New case" default template is the most-used small biopsy. The Part card selector keeps a "Small biopsy" optgroup at the top of the grouped list for mixed cases.

**Three ways in, one picker component**

1. Recent / pinned strip — applies to the Resections row only; keeps ≤ 8 buttons filled from saved-case frequency (Drive sheet `template` column; fall back to a default set), with manual pin / unpin (star in the picker). Small biopsies are already surfaced by the fixed row above and are excluded from this cap.
2. Type-ahead palette — Cmd/Ctrl-K or `/` opens a search over name, organ, `aliases` and diagnosis keywords; Enter selects, ↑↓ move; 2–3 keystrokes reach any template. Primary route once the count is high.
3. Grouped browse — the same palette with nothing typed shows the system × kind grid.

The Part card template selector reuses the same component (grouped by system) since mixed cases already choose templates per part. Keyboard shortcuts do not collide with the numeric option keys (palette only opens from outside a field or via Cmd/Ctrl-K).

**Phase 5 hooks**

- "Upgrade part" action: an unexpected carcinoma in a benign template (gallbladder, thyroid, uterus, appendix, tonsil) converts the part to the matching synoptic template, carrying over macro, site, block key and any shared fields by name; the original values are kept in the case history.
- Registry becomes a metadata-only manifest (`templates/manifest.json` built by `scripts/build-manifest.mjs`: id, name, shortName, system, kind, aliases, version, generator path); generators and schemas are lazy-loaded with dynamic `import()` on first use so initial load does not grow per template. Version pinning per saved case as already planned.
- Settings → Templates: per-user visibility toggles (hide templates never reported) stored with the other settings; hidden templates stay searchable via the palette with a "hidden" tag and can be re-enabled in one click.
- Recently used order and pins sync through the settings record on Drive so they follow the user between browsers.

**Tests:** manifest builder round-trips every schema; small-biopsy row lists exactly the `kind: biopsy` templates in frequency order and survives the pinned cap; palette ranking (exact shortName > alias > organ > keyword); pinned strip caps at 8 and dedupes; lazy-load resolves every manifest entry; upgrade-part preserves macro / block key and reports fields that could not be mapped.

**Done when:** with 40 fixture templates installed, every small-biopsy template is one click from the header, any other template is reachable in ≤ 3 keystrokes from the palette, the Resections row shows only pinned / recent items, the part selector is grouped by system, and initial bundle size is unchanged from the Phase 4 build.

## Risks and mitigations

- **Wording drift during refactor** → golden fixtures from Phase 0, run on every change.
- **OAuth friction** → the consent screen stays in Testing mode (single test user), avoiding verification; if `drive.file` cannot write into the existing folder, widen to the `drive` scope.
- **Preview iframe limits** → sign-in and storage are exercised on the published pplx.app URL, not the in-thread preview; re-publish after each Drive-layer change.
- **PHI on personal Drive** → accession-only guard on free text; no names or HKIDs ever entered.
- **Drive/Sheets API quota or outage** → `sessionStorage` cache of the open case and a retry on save; Copy buttons always work as a manual fallback into the LIS.
- **Staging rule errors** → unit tests per pT/pN boundary from the CAP protocol tables; edition stamped on output so errors are traceable.
- **Case-mix sampling bias** → the Drive folder mostly holds drafted resections, not endoscopic biopsies signed out directly in the LIS, so Phase 4 (GI biopsies) is justified by LIS volume while Phase 4b is justified by the Drive tally; revisit the order if the TAT list says otherwise.
- **Scope creep in Phase 5** → import QMH pages only when you need them; do not convert all 60 up front.
